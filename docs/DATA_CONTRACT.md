# Контракт данных Genesis FinTech

Схемы версии `1.0.0` лежат в [schemas/](../schemas/), решения о формате — в [ADR 0001](ADR/0001-episode-and-schema.md), [ADR 0002](ADR/0002-evaluator-isolation.md) и [ADR 0003](ADR/0003-matching-and-reward.md). Используем JSON Schema Draft 2020-12. URI `https://schemas.genesis.invalid/v1/` служит идентификатором. Проверка использует локальный реестр схем и работает без сетевого разрешения ссылок.

## Файлы эпизода

| Файл | Схема | Содержимое |
| --- | --- | --- |
| `manifest.json` | [manifest](../schemas/manifest.schema.json) | Версия, ID, базовая валюта, границы периода и часовой пояс, валютные разрядности, округление, размеры открытых таблиц и число документов. |
| `ledger.csv` | [ledger-row](../schemas/ledger-row.schema.json) | Проводки. Валидатор получает типизированные строки после разбора CSV. |
| `invoices.jsonl` | [invoice](../schemas/invoice.schema.json) | Счёт и его позиции. Позиции могут содержать описание, количество, цену за единицу и сумму в минимальных единицах. |
| `payments.jsonl` | [payment](../schemas/payment.schema.json) | Платёж. `invoice_refs` содержит список идентификаторов счетов либо явный `null`. Размеры проведённых распределений можно проверить по связанным проводкам. |
| `fx.csv` | [fx-row](../schemas/fx-row.schema.json) | Курс на дату и пару валют, строка проверяется после разбора CSV. |
| `policy.json` | [policy](../schemas/policy.schema.json) | Определяет дату курса, интервал, часовой пояс и округление. Необязательное поле `recognition_date_rule` задаёт дату признания для проверки периода. |
| `findings.json` | [findings](../schemas/findings.schema.json) | Вывод политики для одного эпизода: до 30 выводов, до 64 уникальных `affected_ids`, `claimed_amount_minor` в диапазоне `0..10^18`, до 10 `evidence_ids`, длина ID до 128 символов и до 1 000 символов объяснения на вывод. |
| `trajectories.jsonl` | [trajectories](../schemas/trajectories.schema.json) | Одно действие и наблюдение на строку, с бюджетом, флагами завершения и наградой. |
| `truth.json` | [truth](../schemas/truth.schema.json) | Закрытый перечень ошибок, ожидаемые суммы, валюты и один или несколько допустимых наборов доказательств (`acceptable_evidence_sets`). |
| `provenance.json` | [provenance](../schemas/provenance.schema.json) | Закрытые seed, конфигурация, исходная история и причинные изменения. |
| Конфигурация | [config](../schemas/config.schema.json) | Версия и количества ошибок по типам. Опционально задаются отвлекающие случаи, взаимодействия и параметры масштаба/валют/правил (`obligation_count`, `base_currency`, `foreign_currency`, `timezone`, `fx_date_rule`). Seed передаётся отдельно. |

`document_count` равен сумме счетов и платежей. Политика учёта доступна отдельно как документ с ID `policy`. `record_counts` содержит размеры таблиц `ledger`, `invoices`, `payments` и `fx`.

## Сериализация и ссылки

- JSON, JSONL и CSV в UTF-8. В JSONL каждая строка содержит один JSON-объект. Для CSV используются точные заголовки из ТЗ. Отсутствующие ссылки `invoice_id` и `payment_id` записываются буквальным `null` и при разборе становятся JSON `null`. Поля ссылок обязательны, пустая строка некорректна.
- Валюты обозначаются трёхбуквенными кодами. Денежные поля `*_minor` — целые JSON-числа. Стандарт JSON Schema считает `12.0` целым по значению, но на Python-границе принимается только `type(value) is int`. Это исключает `float` и `bool`, включая числа внутри вложенного документа. CSV-декодер преобразует только целочисленные записи.
- Временная метка хранит дату, время и явное смещение RFC 3339 в форме `+05:00`, `-04:00` или `Z`. Часовой пояс задаётся именем IANA. Интервал полуоткрытый. FX-курс — положительная десятичная строка в обычной записи, например `"495.0000"`. Правило расчёта описано в ADR 0001. Тесты проверяют даты с активированным format checker.
- ID эпизода задаёт область ссылок. Записи `ledger` адресуются по `row_id`, счета и платежи по `invoice_id` и `payment_id`, а документы через `doc_id`. Ключ строки FX формируется как `fx:<date>:<source>:<target>`. Каталог доказательств включает `row_id`, `doc_id`, ключи FX и `policy`. Эталонные наборы доказательств должны состоять из доступных ссылок.
- Канонические типы выводов — `duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff`. Синтаксически допустимые повторы остаются в `findings`, чтобы оценщик мог учесть лишние утверждения как FP.
- Единый канонический состав `affected_ids` одинаков для одиночных и взаимодействующих ошибок (документные `doc_id` и ключи FX/политики относятся к `evidence_ids`, а не к `affected_ids`):
  - `duplicate_invoice`: `invoice_id` и все четыре `row_id` начисления (исходная и дублирующая пары `expense` / `accounts_payable`).
  - `payment_allocation`: `invoice_id`, `payment_id` и изменённые `row_id` распределения — при частичном распределении это пара `accounts_payable` + `suspense` (4 ID), при полном пропуске — `suspense` (3 ID); строка `bank` относится к доказательствам, а не к `affected_ids`.
  - `fx_conversion`: два `row_id` изменённой пары расчёта (дебет и банковский кредит).
  - `period_cutoff`: два `row_id` пары начисления, отражённой вне отчётного периода.
- `acceptable_evidence_sets` в `truth.json` допускает несколько альтернативных полных комплектов доказательств для одной ошибки (например, минимальный арифметически достаточный набор и расширенный диагностический набор в `partial_fx_payment_at_cutoff`). Вывод засчитывается, если все его `evidence_ids` принадлежат публичному каталогу и содержат хотя бы один полный допустимый набор.
- Для `fx_conversion` сумма вывода равна абсолютной разнице между ожидаемой и проведённой суммой в целевых минимальных единицах. Дата курса определяется по `fx_date_rule` в часовом поясе политики.
- Для `period_cutoff` поле `recognition_date_rule: "document_date"` означает признание начисления по `issued_at` первичного счёта. Сравниваются моменты первичного документа и связанной пары проводок относительно интервала `[period_start, period_end)`. При нескольких ошибках `period_cutoff` генератор чередует смещения до `period_start` и на/после `period_end`. В выводе указываются сумма признания и валюта проводок. Проводки и связанный первичный счёт доступны даже при разносе за пределы периода.
- Схемы проверяют формы и ограничения отдельных записей (включая `description`, закрытый перечень 8 кодов ошибок в `observation.schema.json` и перечисление сценариев в `config.schema.json`). Совпадение ID эпизода между файлами, уникальность каталогов, существование ссылок, хронология, неотрицательный остаток `bank`, размеры файлов, валютная согласованность и причинность проверяются отдельно.

## Параметры конфигурации и масштаб

По умолчанию `generate_episode(seed, config)` строит компактный базовый профиль (`obligation_count=4`, `base_currency="KZT"`, `foreign_currency="JPY"`, `timezone="Asia/Almaty"`, `fx_date_rule="payment_date"`). Опциональные поля `config.schema.json` позволяют масштабировать и варьировать эпизоды без нарушения обратной совместимости:

- `obligation_count` (`4..500`): число базовых обязательств до добавления отвлекающих случаев и взаимодействий (позволяет получать книги с 220+ проводками и 100+ документами).
- `base_currency` и `foreign_currency` должны различаться с учётом значений по умолчанию. Поддерживаются `KZT`, `JPY`, `USD`, `EUR`, `GBP`. Разрядности указаны в `manifest.currency_exponents`.
- `timezone`: имя IANA (включая зоны с DST, например `Europe/Berlin`, `America/New_York`, а также `Asia/Almaty` и `UTC`); все смещения и даты курсов вычисляются единообразно через `ZoneInfo`.
- `fx_date_rule` принимает `payment_date` или `invoice_date`. Взаимодействующие сценарии рассчитаны на `payment_date`.
- `episode_id` задаёт явный публичный идентификатор. Формат — `episode-` и 24 шестнадцатеричных символа для исторических открытых данных или 32 для нового закрытого случая. Если поле опущено, обычный генератор сохраняет старый вывод ID из seed для совместимости с открытыми примерами. Закрытый координатор создаёт ID и seed независимо. [Подготовка закрытого прогона](ISOLATION_AND_LEAKAGE.md)

Нулевые счётчики ошибок, опущенный или `false` флаг `include_distractors`, пустой список `interaction_scenarios: []` и значения по умолчанию нормализуются (убираются) в закрытом `provenance`.

## Дубли и распределение платежей

`generate_episode(seed, config)` принимает независимые счётчики `duplicate_invoice` и `payment_allocation`. Генератор выбирает разные полностью оплаченные счета в базовой валюте. В компактном базовом профиле (`obligation_count=4`) доступны два таких счёта; увеличение `obligation_count` пропорционально увеличивает число кандидатов. Если суммарный запрос превышает число подходящих пар, генератор сообщает причину и не выдаёт частичный эпизод. Отдельный детерминированный поток выбирает счета и варианты распределения.

- При дубле один документ подтверждает обязательство, а четыре проводки показывают два полных начисления. Ожидаемое расхождение равно сумме одного начисления.
- При пропущенном или частичном распределении документ платежа и счёт показывают ожидаемую сумму. Дебет по `accounts_payable`, кредит по `bank` и запись по `suspense` позволяют проверить недостающую долю. При пропуске весь дебет уходит в `suspense`, при частичном распределении часть остаётся в `accounts_payable`. Строка `suspense` сохраняет ссылку на платёж и явный `null` в поле счёта. В обоих случаях денежный баланс сохраняется.

## Корректные операции

`include_distractors` по умолчанию выключен. Опущенный флаг и `false` эквивалентны. Нулевые счётчики ошибок и пустой список `interaction_scenarios: []` эквивалентны отсутствующим. Генератор убирает такие значения из конфигурации в закрытом provenance.

При `include_distractors=true` публичные документы позволяют проверить три ситуации:

- Один счёт закрывается двумя платежами с отдельными `doc_id` и `payment_id`. Каждый платёж распределён полностью на момент его проведения. Остаток счёта равен нулю после второго платежа.
- Платёж по другому счёту включает возвращаемую переплату. Исходящий платёж кредитует `bank`, дебетует `accounts_payable` на сумму счёта и `vendor_receivable` на переплату. Возврат дебетует `bank` и кредитует `vendor_receivable` ровно на сумму переплаты. Чистый отток равен сумме счёта.
- Оба счета выставлены тем же контрагентом на равные суммы за разные услуги в разные даты. У них отдельные документы и собственные пары начисления.

Схема платежа допускает необязательные `payment_kind: "refund"` и `refund_of_payment_id`, которые существуют только вместе. Ссылка ведёт к `payment_id` первоначального исходящего платежа. У исходящего платежа и возврата одинаковая валюта и ссылка `invoice_refs`. `amount_minor` возврата положителен, направление задают вид операции и проводки. Обычные документы сохраняют прежнюю форму. Для воспроизводимого примера используйте seed `413`, `error_counts: {}` и включённый флаг.

## Взаимодействующие ошибки

В `interaction_scenarios` можно указать `partial_fx_payment_at_cutoff` и `duplicate_invoice_with_fx`. Каждый сценарий добавляет две ошибки сверх `error_counts` на собственном валютном обязательстве. Порядок во входном списке не влияет на результат. Повтор названия, неизвестный сценарий или недостаток кандидатов для обычных счётчиков приводят к ошибке подготовки эпизода.

- `partial_fx_payment_at_cutoff`. Платёж проводится за 15 минут до конца периода (с корректной UTC-арифметикой для зон с DST). Сначала часть дебета переносится с `accounts_payable` на `suspense`, затем к платежу применяется котировка следующего дня. Нераспределённая сумма равна разнице между начислением по счёту и дебетом `accounts_payable` по платёжному ID. FX-расхождение равно разнице между кредитом `bank` и ожидаемой суммой по курсу дня платежа. Котировки по обе стороны границы опубликованы. В `acceptable_evidence_sets` публикуются как минимальный арифметически достаточный набор, так и расширенный диагностический набор.
- `duplicate_invoice_with_fx`. Сначала пара начисления `expense` и `accounts_payable` отражается повторно с тем же счётом, затем неверная конвертация меняет сумму пары расчёта по связанному платежу. Нормальное начисление по валютному счёту считается по дате `issued_at` в часовом поясе политики. Сумма дубля равна превышению дебетов `expense` над этим начислением. FX-расхождение отдельно проверяется по кредиту `bank` и котировке на день платежа.

Суммы выводов приводятся в целевых минимальных единицах, а `affected_ids` следуют единым каноническим правилам выше для одиночных и взаимодействующих ошибок (если валютный платёж уже частично перенесён в `suspense`, расхождение FX относится к `suspense` и банковскому кредиту). Документы и котировки указываются в `evidence_ids`; котировка фактически применённого неверного дня и строка исходного начисления могут дополнять доказательство, когда расчёт подтверждается остальными записями. У каждой мутации собственный `issue_id` (из изолированного потока ID) и последовательный снимок затронутых строк в `provenance.changes`.

## Действия и журнал

[Схема действия](../schemas/action.schema.json) использует объект с полем `type` и именованными аргументами. Для `list_records` отсутствие курсора или значение `null` означают первую страницу, `limit` при наличии лежит в диапазоне 1–50. `submit` принимает объект формата `findings.json` в поле `findings`. [Наблюдение](../schemas/observation.schema.json) содержит остаток шагов и результат одного действия. Для `reset` используются задача, manifest и политика.

По умолчанию страница содержит до 50 записей в порядке исходной таблицы. Курсор непрозрачен и привязан к таблице и снимку открытых данных текущего эпизода. Конец таблицы даёт курсор `null`. `get_record` использует ключ записи таблицы, а `get_document` — ключ документа или `policy`. Возврат сохраняет исходные денежные значения и поля, которые объявлены в публичной схеме.

Калькулятор принимает десятичные числа, круглые скобки, унарные знаки и операции `+`, `-`, `*`, `/` с обычным приоритетом. Результат — строка в десятичной записи без экспоненты. Контекст использует 34 значащие цифры, `ROUND_HALF_EVEN` и скорректированный показатель в пределах от −48 до 47.

| Ограничение калькулятора | Максимум |
| --- | --- |
| Длина выражения | 256 символов |
| Глубина скобок и унарных знаков | 16 |
| Число операций, включая унарные | 64 |
| Цифр в литерале | 34 |
| Длина результата | 96 символов |

Коды отказа — `invalid_expression`, `division_by_zero` и `calculation_limit`. Эти границы ограничивают ресурсы каждого запроса. За действие отвечает существующий счётчик среды.

Шаги в траектории нумеруются с 1 до 100. Исследовательский шаг до завершения имеет награду 0. Структурно невалидное действие (`invalid_action`, `invalid_argument`, невалидный `submit`) записывается как `{"type":"invalid"}` без копирования исходного ввода; синтаксически валидный вызов инструмента, получивший контролируемую ошибку (`not_found`, `invalid_cursor`, `invalid_expression`, `division_by_zero`, `calculation_limit`, `tool_error`), сохраняется в журнале. Текст `explanation` сохраняется в открытом режиме `train` и обнуляется в закрытом режиме `eval`. Закрытый режим и системная изоляция описаны в [ADR 0002](ADR/0002-evaluator-isolation.md) и [ISOLATION_AND_LEAKAGE.md](ISOLATION_AND_LEAKAGE.md).

## Проверка в репозитории

Установите Python 3.11+, затем зависимости проверок из зафиксированного [lock-файла](../tests/requirements-schema.lock) (при необходимости установите пакет через `pip install --no-deps --no-build-isolation -e .`). Для работы с временными зонами IANA используется `tzdata`; остальное ядро среды опирается на стандартную библиотеку.

```bash
python -m pip install --no-deps -r tests/requirements-schema.lock
python -m pip check
PYTHONPATH=src python -m genesis.cli verify --all
```

```powershell
$env:PYTHONPATH = 'src'
python -m genesis.cli verify --all
```

В [fixtures/contract](../tests/fixtures/contract/) хранится компактный составленный вручную FX-эпизод для модульных проверок контракта (`public/` и `evaluator-only/`). Полный открытый комплект из 10 `train` и 10 `dev` эпизодов находится в [data/](../data/), а реальная многошаговая записанная траектория — в [trajectories/trajectories.jsonl](../trajectories/trajectories.jsonl).
