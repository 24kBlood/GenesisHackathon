# Граница оценщика и внешней политики

Доверенный координатор вызывает `reset(seed, config)`, выбирает эпизод и хранит терминальный отчёт. Внешняя политика работает в отдельном контейнере. Она читает опубликованные данные через ответы разрешённых инструментов и передаёт действие через stdout. Oracle, эталон, provenance, seed и внутренние ошибки остаются у оценщика. Подробности разделения описаны в [ADR 0002](ADR/0002-evaluator-isolation.md).

## Протокол

Координатор отправляет кадр `{"type":"reset","observation":...,"info":{}}`. Затем работник отправляет один объект действия и ждёт кадр `{"type":"step","observation":...,"reward":0,"terminated":false,"truncated":false,"info":{}}`. У действий нет диалога сброса. Валидное JSON-сообщение с неизвестным действием или неверными аргументами обрабатывает среда. Неизвестный ID получает публичную ошибку.

Каждый кадр заканчивается LF. Предел stdin/stdout равен 512 КиБ, включая LF. Невалидный UTF-8, одиночные суррогаты UTF-16 (`\ud800`–`\udfff`, отклоняются итеративной проверкой `_reject_surrogates` в `JsonlProcess.receive` и проверкой строк в `AuditorEnv`), некорректный JSON, повторный ключ объекта, непредставимое конечным числом значение и превышение лимита прерывают транспорт кодом `bad_frame` / `frame_limit`. Stderr отделён от потока сообщений, ограничен 8 КиБ полезных байтов на строку и 64 КиБ за эпизод, включая разделители в общем размере. Его содержимое отбрасывается. Дедлайн проверяется по монотонным часам для запуска, чтения и записи. Сбой протокола до принятия подачи сохраняет доверенный код причины и усечённый итог с `F1 = 0` и наградой `−1`. Невозможность запустить инфраструктуру прерывает оценку. При обрыве или тайм-ауте на отправке финального подтверждения после уже принятого `submit` эпизод не переклассифицируется в транспортный сбой, а результат вычисляется после завершения изоляции.

В закрытом режиме после `submit` координатор отправляет нейтральный итоговый кадр с наградой 0 и завершает работу контейнера до чтения терминального отчёта. Matcher выполняется после подтверждённого удаления контейнера. Если удаление подтвердить не удалось, координатор возвращает ошибку инфраструктуры (`PolicyCleanupError`) и закрытая оценка не выполняется; при этом проверка отсутствия контейнера (`_container_absent`) получает собственный ограниченный таймаут, чтобы сбой `docker create` при медленном `docker rm` не маскировался под ошибку очистки. В открытом режиме среда вычисляет терминальную награду, которую получает политика. В обоих режимах подробная диагностика (включая `validation_error` при невалидном `submit`) доступна только стороне оценщика.

## Запуск контейнера

Доверенный оператор заранее готовит локальный Linux-образ с кодом политики и указывает его при создании `DockerPolicy` (для встроенных публичных политик предусмотрен [`Dockerfile.policy`](../Dockerfile.policy)). Образ выбирается по неизменяемому ID через компактный `docker image inspect --format` (что исключает сбои из-за >64 КиБ метаданных многослойных образов), автоматическая загрузка образа отключена. Образы с объявленными томами (`Config.Volumes`) или активным `Config.Healthcheck` отклоняются. Вызов Docker выполняется без оболочки. Управляющему хостовому Docker CLI передаётся только ограниченный белый список переменных окружения (`PATH`, `SYSTEMROOT`, `WINDIR`, `DOCKER_HOST`, `XDG_RUNTIME_DIR`, `DOCKER_CONTEXT` — для совместимости с rootless Docker и пользовательскими контекстами), а сам контейнер политики не получает переменных окружения хоста.

Политика работает с UID/GID 65532, без сети и IPC, с корнем только для чтения, без Linux capabilities, с `no-new-privileges`, `--no-healthcheck`, `--ulimit nofile=256:256` и `--cgroupns private`. По умолчанию пределы составляют `32` PID, `512` МиБ памяти вместе со swap и `1` ядро CPU. Координатор может поднять ресурсы в конструкторе `DockerPolicy` до `2` CPU и `4` ГиБ RAM и подключить ограниченный `tmpfs` для `/tmp` (`--tmpfs /tmp:rw,nosuid,nodev,noexec,size=<N>m,mode=1777`). Политика получает только свои потоки и временную директорию, если она запрошена; bind mounts, подключённые тома и сокет Docker остаются за пределами контейнера. Docker создаёт обычные системные псевдофайловые системы контейнера и не сохраняет stdout/stderr политик в драйвер журналирования (`--log-driver none`). При выходе или дедлайне координатор закрывает канал, останавливает процесс подключения и удаляет именованный контейнер с томами.

## Воспроизводимая проверка

Обычные тесты запускают отдельные процессы с синтетическими публичными действиями. Они сравнивают публичные байты при разных эталонах, проверяют порядок закрытой оценки, ошибки транспорта (включая суррогаты, дубли ключей, `NaN`, переполнение кадра и stderr) и итог после молчания и EOF. Эти тесты проверяют протокол и разделение процессов. Системные ограничения проверяет отдельный GitHub Actions job `Policy isolation` на Linux через сборку `Dockerfile.policy` и smoke-образа, фактический запуск контейнера, `docker inspect` и `python -m genesis.cli verify --all --require-docker`.

```sh
docker build --tag genesis-policy-smoke:local tests/fixtures/policy_smoke
docker build -f Dockerfile.policy --tag genesis-policy:local .
GENESIS_POLICY_SMOKE_IMAGE=genesis-policy-smoke:local PYTHONPATH=src \
  python -m genesis.cli verify --all --require-docker
```

Раннер рассчитан на доверенный локальный Docker Engine с Linux-контейнерами и отдельно проверенный образ. Подготовка образа может требовать доступа к реестру (либо локального каталога wheel-файлов через `PIP_FIND_LINKS`). Сам прогон политики работает без сети. Подробности единой офлайн-проверки описаны в [OFFLINE_RUN.md](OFFLINE_RUN.md).
