# Публичные траектории v1

[Траектория](../trajectories/trajectories.jsonl) записана реальным запуском `simple_reconciliation` на масштабированном 60-обязательном эпизоде из `data/train` — `episode-ce7be9493ab47ff2dd4555c4` (`seed=20260110`), содержащем все четыре типа ошибок (`duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff`), оба сценария взаимодействия и отвлекающие операции. В файле один эпизод и **11 принятых шагов**: 10 исследовательских шагов (включая постраничное чтение таблиц с курсорами) дают нулевую награду, 11-й шаг (`submit`) подаёт 8 обоснованных выводов (8 TP / 0 FP / 0 FN) с сохранёнными пояснениями и возвращает в открытом режиме `train` терминальную награду `0,98`.

Размер файла — `111 377` байт, SHA-256 — `2bf23bf9191b1cf1953818a4d3aff650c0a2572fc1fb2162d381587a699273b6`.

## Регенерация и replay

Из корня репозитория на Python 3.11+ с установленными зависимостями из [тестового lock-файла](../tests/requirements-schema.lock):

```sh
PYTHONPATH=src python tests/test_trajectories.py --export
PYTHONPATH=src python -m unittest discover -s tests -p test_trajectories.py -v
```

В PowerShell задайте `$env:PYTHONPATH = 'src'` перед запуском. Команда экспорта перезапишет указанный выше файл из открытого `data/train` эпизода (`seed=20260110`) и проверит строки локальным реестром схем. Тест replay берёт действия из файла, передаёт их в среду и сравнивает получившиеся байты. Кодировка UTF-8, ключи отсортированы, разделитель и окончание строк LF.

## Граница публичных данных

Доверенный координатор подключает `TrajectoryRecorder(mode=...)` через `await run_episode(..., on_step=recorder.record)`. Каждый новый прогон получает свой recorder. Метод `to_jsonl()` сериализует разрешённые поля. Для проверки можно передать `validate_shape` в `validate_trajectory` из локального реестра [схемы траектории](../schemas/trajectories.schema.json). Внешний экспорт создаётся только для обычной политики на проверенных синтетических данных. Эталон, источник данных, диагностика, `info`, stderr и измеренное время остаются вне файла. Oracle в публичном наборе отсутствует.

Различие режимов `train` и `eval`:

- В открытом режиме `train` терминальный шаг записывает фактическую награду, а текст `explanation` в выводах `submit` **сохраняется** для отладки и анализа.
- В закрытом режиме `eval` награда в каждой строке равна нулю (включая завершающий `submit`), а текст `explanation` в выводах заменяется пустой строкой `""` (структурированные `affected_ids`, `evidence_ids`, суммы и валюты сохраняются, поэтому замена не влияет на сопоставление).

Обработка ошибок действий:

- Синтаксически валидные вызовы инструментов, вернувшие контролируемую ошибку инструмента (`not_found`, `invalid_cursor`, `invalid_expression`, `division_by_zero`, `calculation_limit`, `tool_error`), **сохраняются** в поле `action` вместе с публичным кодом ошибки в наблюдении, что позволяет воспроизводить такие шаги при replay.
- Структурно невалидные действия (`invalid_action`, `invalid_argument`, невалидный `submit`) заменяются маркером `{"type":"invalid"}` без копирования исходного ввода. При невалидном `submit` сохраняются флаг завершения и нейтральный статус `submitted`; подробная причина (`validation_error`) остаётся только в доверенном `TerminalResult`.

`reset` и timeout до принятия очередного действия не добавляют строку. Бюджетное усечение следует за сотым принятым действием и записывается на нём. При timeout или обрыве транспорта файл может закончиться префиксом без терминальной строки. Причина усечения и фактическое число принятых действий остаются в отдельной доверенной диагностике.
