# ADR 0001. Эпизод и модель данных

**Статус** — предложено. Основание — ТЗ FinTech §02–03, §06 и §10.

## Решение

Эпизод моделирует одну компанию за один период. Генератор получает `seed`, нормализованную конфигурацию и версию. Использует локальные генераторы случайных чисел для истории, изменений и порядка записей. Каждый этап получает собственный поток, а сериализация задаёт порядок полей, переносы строк и кодировку UTF-8. Для одинаковых входов и версии совпадают записи, ID и закрытый эталон.

1. Сформировать финансовую историю с выписанными счетами, операциями, распределениями платежей, курсами и ожидаемыми проводками. Проверить равенство входящих и исходящих сумм связанных записей в соответствующих валютах и сохранение сумм при распределении.
2. Построить согласованные открытые документы с правдоподобными корректными отвлекающими случаями. Разбитые платежи, возвраты и повторяющиеся суммы должны объясняться документами и политикой.
3. Применить детерминированные причинные изменения. Включение каждого из четырёх типов настраивается отдельно. Для каждого изменения записывать затронутые объекты, состояние до и после и способ расчёта. Эталон связывается с записями, которые реально можно запросить.
4. Проверить инварианты исходной истории, ссылки, форматы, ожидаемое расхождение после изменений, согласованность manifest и доступность каждого объявленного набора доказательств.

| Случай | Наблюдаемое различие |
| --- | --- |
| Дубль счёта | Две финансовые записи относятся к одному подтверждённому обязательству. Сумма и контрагент сами по себе не доказывают дубль. |
| Пропущенное или частичное распределение платежа | Документ подтверждает полученную сумму и назначение, а распределение по связанным счетам отсутствует или расходится с этим назначением. |
| Неверный FX | Курс для даты и пары валют, выбранных по `policy.json`, даёт сумму, отличную от отражённой в проводке. |
| Ошибка отчётного периода | Дата, по которой политика относит документ к периоду, расходится с периодом отражённой проводки. |

Предлагаемые сочетания — частично распределённый валютный платёж с ошибкой FX или периода на границе периода и дубль счёта с сопутствующей ошибкой FX. В обеих конфигурациях документируем причинную цепочку. Для каждой эталонной ошибки сохраняем собственный проверяемый вывод, даже при общих доказательствах. Чистая конфигурация формирует пустой список ошибок, сохраняя корректные отвлекающие случаи.

## Файлы и типы

| Данные | Файл и формат |
| --- | --- |
| Метаданные | `manifest.json` с `schema_version`, `episode_id`, `base_currency`, `period_start`, `period_end`, `timezone`, количеством записей и документов, разрядностями валют и правилами округления. |
| Проводки | `ledger.csv` с `row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id`. |
| Счета | `invoices.jsonl` с `doc_id,invoice_id,entity_id,issued_at,due_at,currency,total_minor,line_items`. |
| Платежи | `payments.jsonl` с `doc_id,payment_id,timestamp,currency,amount_minor,invoice_refs`. |
| Курс и политика | `fx.csv` с `date,source_currency,target_currency,rate`. `policy.json` описывает выбор даты курса, границы периода, часовой пояс и округление. |
| Скрытое | `truth.json` с типом, `issue_id`, `affected_ids`, `expected_amount_minor`, `currency` и допустимыми наборами доказательств. `provenance.json` хранит исходную историю и причинные изменения. Оба файла доступны оценщику. |

Машиночитаемые схемы и точные имена полей расширений оформляются в [SCHEMA-02](https://github.com/24kBlood/GenesisHackathon/issues/8). Отсутствующие связи в JSON равны `null`. Для nullable полей CSV предлагаем единый литерал `null`, который декодируется в JSON `null`. Обязательные поля CSV проверяются отдельно от JSON Schema.

Денежное поле `*_minor` хранит целое количество минимальных единиц с разрядностью из manifest. Формат FX — десятичная строка. Для курса, заданного как единицы целевой валюты за одну единицу исходной, переводим minor units в major units, умножаем на `Decimal(rate)`, переводим в minor units целевой валюты и округляем согласно опубликованной политике на согласованном этапе. Временные метки имеют смещение ISO-8601. Сравнение периода делаем в часовом поясе компании, предлагаемый интервал — `[period_start, period_end)`.

Идентификаторы ограничены эпизодом, устойчивы при повторе и непрозрачны. Внешние доказательства указывают на однозначные публичные записи. Если типы записей используют разные пространства ID, каталог доказательств выдаёт однозначные публичные ссылки. Упорядочивание, имена и ID варьируются независимо от наличия ошибки. При парной проверке биекция применяется ко всем первичным ID, ссылкам, эталону и доказательствам.

## Какие проверки добавим

- Отдельный эпизод для каждого типа, оба взаимодействующих случая и чистые конфигурации с отвлекающими случаями. Для каждого изменения проверяем фактическую величину расхождения и доступность доказательств.
- Границы периода со смещениями, валюты с разной разрядностью, правило выбора даты курса, округление на границе половины единицы и nullable-связи.
- Идентичные данные при повторе seed, конфигурации и версии. Перестановка и биекция сохраняют вердикт Oracle и награду.
